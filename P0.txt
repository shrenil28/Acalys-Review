# Acalys Review — Phase 0: Canonical Contracts & Architectural Foundation

You are implementing **Phase 0 of Acalys Review**, a production-grade cloud code-review platform whose first architectural baseline is modeled after the capabilities and separation of concerns of systems such as CodeRabbit.

This phase is deliberately **not about implementing the LLM reviewer, GitHub webhook handling, repository cloning, static-analysis tools, sandbox execution, or multi-agent review yet**.

Phase 0 exists to establish the **canonical domain model, contracts, state machines, schemas, validation boundaries, identifiers, events, package boundaries, persistence-facing abstractions, and provider-neutral interfaces** on which every later subsystem will depend.

This is foundational work.

Do not treat it as a collection of TypeScript interfaces that can be casually changed later.

The Phase 0 contracts must be designed as if the following future systems will all depend on them:

* GitHub
* GitLab
* Bitbucket in the future
* local CLI review
* IDE review
* web review UI
* webhook gateway
* review scheduler
* durable workflow engine
* repository snapshot service
* sandbox workers
* static-analysis workers
* repository intelligence
* AST/symbol graph
* evidence system
* Review Agent
* Verification Agent
* Chat Agent
* Pre-Merge Agent
* incremental re-review
* review memory
* organization/repository knowledge
* CI ingestion
* runtime reproduction
* fix agent
* `/review`
* `/deep-review`
* model routing
* billing
* observability
* evaluation infrastructure

The result of Phase 0 should make it possible for all later components to communicate through **stable canonical contracts instead of provider-specific, agent-specific, or database-specific structures**.

---

# 1. Core architectural principle

The entire platform must obey:

```text
External Provider Representation
             ↓
       Adapter Boundary
             ↓
    Canonical Acalys Contracts
             ↓
       Internal Platform
             ↓
       Adapter Boundary
             ↓
 External Provider Representation
```

For example:

```text
GitHub PullRequest
       ↓
GitHub Adapter
       ↓
Acalys ReviewTarget
       ↓
Review Platform
```

and never:

```text
GitHub PullRequest
       ↓
ReviewAgent
```

No core review package should need to understand GitHub webhook payload structures.

Likewise:

```text
GitLab merge request
       ↓
GitLab Adapter
       ↓
same ReviewTarget
```

and:

```text
local working tree
       ↓
CLI Adapter
       ↓
same ReviewTarget
```

Provider-specific logic must terminate at the provider boundary.

Before changing architecture:

1. inspect the complete repository structure;
2. inspect workspace configuration;

# 5. Branded identifiers

Do not represent every identifier as a plain `string`.

Introduce type-safe IDs.

Conceptually:

```ts
type Brand<T, Name extends string> =
  T & { readonly __brand: Name };

type OrganizationId = Brand<string, "OrganizationId">;
type UserId = Brand<string, "UserId">;
type RepositoryId = Brand<string, "RepositoryId">;
type PullRequestId = Brand<string, "PullRequestId">;
type PullRequestRevisionId = Brand<string, "PullRequestRevisionId">;
type ReviewRequestId = Brand<string, "ReviewRequestId">;
type ReviewRunId = Brand<string, "ReviewRunId">;
type FindingId = Brand<string, "FindingId">;
type EvidenceId = Brand<string, "EvidenceId">;
type ConversationId = Brand<string, "ConversationId">;
type CommentId = Brand<string, "CommentId">;
type ArtifactId = Brand<string, "ArtifactId">;
```

Implement safe factory/validation helpers.

Do not allow accidental assignment such as:

```ts
const reviewRunId: ReviewRunId = repositoryId;
```

IDs must be safe for distributed generation.

A sortable UUID strategy such as UUIDv7 is acceptable if compatible with the existing stack.

Centralize generation.

Do not have each package invent its own ID scheme.

# 6. Timestamp conventions

Use one canonical serialized representation.

Recommended:

```text
RFC 3339 / ISO 8601 UTC
```

Example:

```text
2026-08-15T15:30:12.421Z
```

At runtime, clearly distinguish:

```text
serialized timestamp
```

from:

```text
Date object
```

Avoid ambiguous local timestamps.

All persisted review-domain timestamps should be UTC.

# 7. Schema versioning

Every long-lived externally transported top-level contract must be versionable.

For example:

```ts
interface VersionedContract {
  schemaVersion: number;
}
```

or an equivalent robust mechanism.

Do not randomly add version properties everywhere.

Define:

* which objects require explicit schema versions;
* which are nested internal values;
* compatibility rules;
* migration strategy;
* decoding behavior for unsupported versions.

Consider versioning at major contract boundaries such as:

```text
ReviewTarget
ReviewRequest
ReviewRunSnapshot
ChangeManifest
ReviewFinding
Evidence
ReviewConfig
DomainEvent
```

The design must support future schema evolution without silent corruption.

# 8. Canonical provider model

For example:

```ts
type SourceProvider =
  | "github"
  | "gitlab"
  | "bitbucket"
  | "local";
```

But architect this so provider growth does not require rewriting the domain.

Define provider references:

```ts
interface ProviderReference {
```

Potential provider-scoped references:

```text
installation
organization
repository
pull request
comment
user
check run
```

Never assume GitHub numeric PR numbers are globally unique.

It should distinguish:



```ts
interface Repository {

  organizationId: OrganizationId;

  provider: SourceProvider;

  providerRepositoryId: string;

  owner: string;
  name: string;

  defaultBranch?: string;

    | "unknown";

    | "active"
    | "disabled"
    | "archived";
```

Do not encode GitHub-specific fields into this core object.

Avoid uncontrolled:

```ts

```

If metadata is necessary, constrain and document it.

```ts
interface PullRequestReviewTarget {
```

# 17. Review execution modes

The architecture must already account for:

```text
/review
/deep-review
```

without implementing swarm behavior yet.

Define:

```ts
type ReviewExecutionMode =
  | "review"
  | "deep_review";
```

Or clearer internal names:

```ts
type ReviewExecutionStrategy =
  | "single"
  | "swarm";
```

Potentially separate user-facing mode from execution strategy:

```ts
interface ReviewExecutionPolicy {
  mode: "review" | "deep_review";
  strategy: "single" | "swarm";
}
```

Important invariant:

```text
/review
→ single reviewer

/deep-review
→ reviewer swarm
```

Everything else should eventually use the same review pipeline.

Do not implement different finding semantics or severity logic between these modes.

# 18. ReviewRun

A ReviewRun is one concrete execution attempt.

A request may potentially produce more than one run because of:

* retries
* manual reruns
* recovery
* future shadow evaluation
* alternate model experiments

Define:

```ts
interface ReviewRun {
  id: ReviewRunId;

  requestId: ReviewRequestId;

  organizationId: OrganizationId;
  repositoryId: RepositoryId;

  target: ReviewTargetReference;

  revisionId?: PullRequestRevisionId;

  state: ReviewRunState;

  executionMode: ReviewExecutionMode;

  attempt: number;

  startedAt?: Timestamp;
  completedAt?: Timestamp;

  failure?: ReviewRunFailure;
}
```

Keep request intent separate from execution attempt.

# 19. ReviewRun state machine

Do not define lifecycle merely as arbitrary strings.

Implement an explicit state machine.

Initial states:

```text
QUEUED
  ↓
PREPARING
  ↓
ANALYZING
  ↓
REVIEWING
  ↓
VERIFYING
  ↓
RECONCILING
  ↓
PUBLISHING
  ↓
COMPLETED
```

Terminal/error branches:

```text
FAILED
CANCELLED
SUPERSEDED
```

Potential canonical values:

```ts
type ReviewRunState =
  | "queued"
  | "preparing"
  | "analyzing"
  | "reviewing"
  | "verifying"
  | "reconciling"
  | "publishing"
  | "completed"
  | "failed"
  | "cancelled"
  | "superseded";
```

Implement allowed transitions.

For example:

```text
queued -> preparing
preparing -> analyzing
analyzing -> reviewing
reviewing -> verifying
verifying -> reconciling
reconciling -> publishing
publishing -> completed
```

Do not allow:

```text
completed -> analyzing
```

without creating a new run.

Expose transition validation functions.

Example:

```ts
assertValidReviewRunTransition(from, to);
```

Test every legal and illegal transition.

# 22. SourceLocation

Support:

* file
* line
* line range
* side/base/head
* commit
* symbol
* optional column
* deleted lines
* renamed files

Example:

```ts
interface SourceLocation {
  repositoryId: RepositoryId;
```

Separate them.

The review agent produces:

```text

```

```text
ReviewFinding
```

Candidate:

```ts
interface CandidateFinding {
  id: CandidateFindingId;

  reviewRunId: ReviewRunId;

  claim: string;

  explanation: string;

  location: SourceLocation;

  evidence: EvidenceReference[];

  createdAt: Timestamp;
```

Verified/published finding:

```ts
interface ReviewFinding {
  schemaVersion: number;

  id: FindingId;

  reviewRunId: ReviewRunId;

  title: string;

  explanation: string;

  category: FindingCategory;

  severity: FindingSeverity;
```

Do not let candidate and published finding share exactly the same type.

They have different semantics.

# 25. Severity

Define severity semantically.

Suggested:

```ts
type FindingSeverity =
  | "critical"
  | "high"
  | "medium"
  | "low"
  | "info";
```

Document what each means.

For example:

### Critical

Likely catastrophic or immediately exploitable:

* remote code execution
* authentication bypass
* severe data corruption
* credential exposure
* destructive production failure

### High

Major correctness/security/reliability issue with meaningful impact.

### Medium

Real bug or substantial issue that should normally be fixed.

### Low

Limited impact issue.

### Info

Useful observation not normally blocking.

Keep severity separate from confidence.

A critical issue may have low confidence while under investigation.

# 63. Security requirements

Even though Phase 0 does not execute untrusted code, contracts must be safe.

Rules:

* never include provider access tokens in domain events;
* never include credentials in ReviewTarget;
* never embed secret environment variables;
* never persist raw OAuth tokens inside review entities;
* never allow arbitrary filesystem paths where repository-relative paths are expected;
* normalize paths;
* reject path traversal;
* cap untrusted string sizes at API boundaries;
* validate URLs before future use;
* avoid prototype-pollution-prone object handling;
* use safe JSON parsing;
* prohibit unserializable values;
* avoid functions/classes inside transport contracts.

# 129. Acceptance criteria

Phase 0 is complete only when all of these are true.

## Architecture

* provider-specific types do not leak into canonical review contracts;
* persistence technology does not leak into domain contracts;
* model-provider types do not leak into finding/evidence contracts;
* review targets support PR and future non-PR reviews;
* PR revisions are immutable first-class objects;
* ReviewRequest and ReviewRun are separate concepts;
* review execution mode supports single and future swarm execution;
* candidate and verified/published findings are separate;
* evidence is first-class;
* verification is first-class;
* finding lifecycle is explicit;
* incremental-review lineage can be represented;
* configuration snapshots can be represented;
* artifacts are references rather than giant inline blobs;
* events are versioned and traceable.

## Type safety

* no avoidable `any`;
* external data enters through `unknown`;
* all important boundaries use runtime schemas;
* discriminated unions are exhaustive;
* branded IDs prevent category mistakes.

## Correctness

* all state transitions are tested;
* invalid transitions fail;
* invalid paths fail;
* invalid IDs fail;
* invalid timestamps fail;
* invalid confidence scores fail;
* invalid line ranges fail;
* invalid schema versions fail.

## Distributed-system readiness

* idempotency is modeled;
* correlation/causation can be modeled;
* retryability is represented;
* supersession is represented;
* cancellation is represented or explicitly delegated;
* immutable revision/config identities exist.

## Testing

All:

```text
typecheck
lint
unit tests
contract tests
fixture tests
build
```

must pass.

No skipped failing tests.

No commented-out tests.

No test-only hacks in production code.

# 132. Critical architectural invariants

```text
GitHub != domain model

PullRequest != PullRequestRevision

ReviewRequest != ReviewRun

CandidateFinding != ReviewFinding

Evidence != Finding

Review finding != Pre-merge check

Review Agent != provider API

Large tool output != queue payload

Provider ID != Acalys ID

```

```text
                   Provider Adapters
                          ↓

                          ↓
                 Review Platform
                          ↓
```

Never reverse that dependency direction.
